# RSA1006: `SubscribeOn` only supports a single use per pipeline

| Property | Value |
|-|-|
| **Rule ID** | RSA1006 |
| **Category** | Usage |
| **Default severity** | Suggestion |
| **Enabled by default** | Yes |
| **Code fix** | No |

## Cause

A single observable pipeline called `.SubscribeOn(...)` more than once.

## Rule description

`SubscribeOn` schedules the *subscription side-effect* (where `Subscribe` runs), not the values
flowing through the pipeline. Only the scheduler from the SubscribeOn call closest to the source
actually takes effect; every later `SubscribeOn` in the same chain is dead code that reads as
though it changes behavior but does not.

```csharp
Observable
   .Return(Unit.Default)
   .SubscribeOn(TaskPoolScheduler.Default)
   .SubscribeOn(ImmediateScheduler.Instance); // has no effect
```

## How to fix violations

Remove every `SubscribeOn` call but the one that should win, or split the pipeline so each
`SubscribeOn` sits on its own chain. There is no mechanical fix because which call was meant to win
is a judgment call about the pipeline's intent — RSA1006 has no code fix.

## When to suppress warnings

Suppress only for a pipeline you've deliberately verified only the first `SubscribeOn` matters and
the later ones are being kept as documentation of an alternative scheduler considered. That's rare;
prefer deleting the redundant call.

## Suppress a warning

```csharp
#pragma warning disable RSA1006 // Multiple attempts to subscribe on a thread scheduler
#pragma warning restore RSA1006
```

```ini
[*.cs]
dotnet_diagnostic.RSA1006.severity = none
```

See [Suppress a warning](../README.md#suppress-a-warning) in the package README for the
`SuppressMessageAttribute` form and when to prefer it over `.editorconfig`.
