# RSA0005: Do not use ?., ??, or ??= where flow analysis already proves the operand non-null

| Property | Value |
|-|-|
| **Rule ID** | RSA0005 |
| **Category** | Nullability |
| **Default severity** | Info |
| **Enabled by default** | Yes |
| **Code fix** | No |

## Cause

`?.`, `??`, or `??=` is applied to an operand whose declared type is nullable-annotated, but whose
nullable flow state at that point has already been narrowed to definitely-not-null - typically by
an earlier null check, a narrowing assignment, or a pattern match.

## Rule description

`?.`, `??`, and `??=` exist to handle a value that might be null. When the compiler's own flow
analysis has already proven the operand can't be null here, the operator isn't handling anything -
it's defensive code left behind after the nullability was already resolved:

```csharp
// Violates RSA0005
string? value = "literal";
var length = value?.Length; // value cannot be null here; ?. is redundant
```

```csharp
public int? Read(string? value)
{
    if (value != null)
    {
        return value?.Length; // value is already narrowed non-null in this branch
    }

    return null;
}
```

```csharp
// Satisfies RSA0005
string? value = "literal";
var length = value.Length;
```

**An operand whose declared type was never nullable is out of scope entirely.** This rule only
targets an operand annotated `T?` whose flow state is narrowed - not one declared as plain `T` used
defensively, which is a different, much broader style question this rule doesn't take a position
on.

**A nullable-oblivious region (`#nullable disable`) is out of scope**, since flow state isn't
meaningfully tracked there at all. See [RSA0008](RSA0008.md), which flags the directive that
creates that region in the first place.

This is the mirror image of the compiler's own CS8602 (possible null reference): CS8602 fires when
flow analysis says an access *might* be unsafe; this rule fires where an operator exists to guard
against null and flow analysis says the guard cannot ever trigger. It is also adjacent to, but the
opposite direction from, the built-in IDE0031 (use null propagation), which suggests *adding* `?.`/
`??` where a value can be null.

## How to fix violations

Remove the `?.`, `??`, or `??=` and access, assign, or use the value directly.

## When to suppress warnings

Suppress where the narrowing is fragile against a future edit - for example, an early return that a
later refactor might remove, after which the operator would become load-bearing again - and the
defensive form is intentionally being kept as insurance.

## Suppress a warning

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage("Nullability", "RSA0005:Do not use ?., ??, or ??= where flow analysis already proves the operand non-null", Justification = "<explain why>")]
```

```csharp
#pragma warning disable RSA0005 // '{0}' is proven non-null at this point; the null-conditional or null-coalescing operator here is defensive noise
#pragma warning restore RSA0005
```

```ini
[*.cs]
dotnet_diagnostic.RSA0005.severity = none
```

See [Suppress a warning](../README.md#suppress-a-warning) in the package README for the
`SuppressMessageAttribute` form and when to prefer it over `.editorconfig`.
