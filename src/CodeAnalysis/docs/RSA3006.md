# RSA3006: Use Observable.Create instead of Observable.FromEvent

| Property | Value |
|-|-|
| **Rule ID** | RSA3006 |
| **Category** | Performance |
| **Default severity** | Warning |
| **Enabled by default** | Yes |
| **Code fix** | Yes |

## Cause

A call to `System.Reactive.Linq.Observable.FromEvent(...)` or `Observable.FromEventPattern(...)`.

## Rule description

The Rx event bridges are general purpose, and they pay for it on every subscription:

- Every subscription goes through an internal event producer that takes a lock and reference-counts a
  shared session.
- Without an explicit scheduler, they capture the current `SynchronizationContext` to add and remove
  the handler.
- They allocate conversion delegates.
- `FromEvent<TDelegate, TEventArgs>(addHandler, removeHandler)` builds its conversion delegate with
  reflection.
- `FromEventPattern(target, "EventName")` and `FromEventPattern(typeof(T), "EventName")` find the
  event and create the handler with reflection. That is slow, and it is not safe under trimming or
  native AOT.

An `Observable.Create` that adds the handler on subscribe and removes it on dispose does the same
job with none of that overhead.

RSA3006 applies to every `FromEvent` and `FromEventPattern` overload on `System.Reactive.Linq.Observable`.

## How to fix violations

Subscribe to the event directly inside `Observable.Create`, and remove the handler in the returned
disposable.

```csharp
// Violates RSA3006
Observable.FromEvent<PropertyChangingEventHandler, PropertyChangingEventArgs>(
    handler =>
    {
        void Handler(object sender, PropertyChangingEventArgs args) => handler(args);
        return Handler;
    },
    handler => source.PropertyChanging += handler,
    handler => source.PropertyChanging -= handler);
```

```csharp
// Satisfies RSA3006
Observable.Create<PropertyChangingEventArgs>(observer =>
{
    void Handler(object sender, PropertyChangingEventArgs args) => observer.OnNext(args);
    source.PropertyChanging += Handler;
    return Disposable.Create(() => source.PropertyChanging -= Handler);
});
```

`FromEventPattern` becomes the same shape, with `observer.OnNext(new EventPattern<TEventArgs>(sender, e))`.

### Code fix

The code fix rewrites the call to `Observable.Create` and adds `using System.Reactive.Disposables;`
when it is missing. It keeps your own conversion lambda: each call to its handler parameter becomes
`observer.OnNext(...)`.

The code fix is not offered when it can't produce an equivalent rewrite:

- The overload takes an `IScheduler`. The scheduler controls where the handler is added and
  removed, and `Observable.Create` has no direct equivalent.
- The add or remove handler, or the conversion, is a method group or something else that isn't a
  lambda.
- A reflection overload names an event that can't be resolved on the target's compile-time type.
  The same applies when the event name isn't a constant, or when the target expression could have
  side effects (it would be evaluated twice).

## Behavior differences

Review these before you accept the fix:

- **One handler per subscriber.** `FromEvent` shares one underlying handler across concurrent
  subscribers. `Observable.Create` adds a handler for each subscription. Add `.Publish().RefCount()`
  if you need the sharing.
- **No `SynchronizationContext` capture.** The handler is added and removed on the thread that
  subscribes and disposes. `FromEvent` without a scheduler posts those calls to the
  `SynchronizationContext` captured at subscribe time.

## When to suppress warnings

Suppress when you rely on either behavior above, or when the call isn't on a hot path and you'd
rather keep the shorter form.
