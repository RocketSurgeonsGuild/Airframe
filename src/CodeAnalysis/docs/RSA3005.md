# RSA3005: AutoRefresh already applied for this property

| Property | Value |
|-|-|
| **Rule ID** | RSA3005 |
| **Category** | Performance |
| **Default severity** | Warning |
| **Enabled by default** | Yes |
| **Code fix** | No |

## Cause

A call to DynamicData's `AutoRefresh(...)` targets the same property as another `AutoRefresh(...)`
call within the same pipeline construction — whether both calls are further down the same fluent
chain, sit in separate source pipelines that are combined by an Rx combinator (`Merge`,
`CombineLatest`, `Zip`, `Concat`, `Switch`, ...), or are built in separate local variables that are
later combined that way.

## Rule description

Each `AutoRefresh(...)` call subscribes to property-change notifications and re-evaluates the change
set on every change for the property (or properties) it targets. Applying `AutoRefresh` more than
once for the same property sets up that re-evaluation work redundantly — the second call buys
nothing the first one didn't already provide, at the cost of a second subscription and a second pass
of re-evaluation work per change. This still holds once two independently auto-refreshed pipelines
are combined into one, since the combined pipeline re-evaluates the property redundantly regardless
of which source it came from. RSA3005 only compares selectors it can confidently normalize to a
plain member-access path (e.g. `x => x.Thing` or `x => x.Foo.Bar`); a selector shaped any other way
(a conditional expression, a method call, or anything else that isn't a plain accessor chain) is left
uncompared rather than risk a false positive — false negatives are the intended, safer failure mode
here. Likewise, a local variable's AutoRefresh pipeline is only followed to a later combinator when
its data flow is unambiguous (a single declaration with an initializer); a variable assigned across
multiple branches, or a method parameter with no visible initializer, is left uncompared for the same
reason.

## How to fix violations

Remove the redundant `AutoRefresh(...)` call, keeping the one that already covers the property.

```csharp
// Violates RSA3005 - same fluent chain
cache
   .Connect()
   .AutoRefresh(x => x.Thing)
   .AutoRefresh(x => x.Thing)
   .Subscribe();
```

```csharp
// Satisfies RSA3005
cache
   .Connect()
   .AutoRefresh(x => x.Thing)
   .Subscribe();
```

```csharp
// Violates RSA3005 - same property re-evaluated after two separately-sourced AutoRefresh
// pipelines are combined
Observable.Merge(
    cacheA.Connect().AutoRefresh(x => x.Thing),
    cacheB.Connect().AutoRefresh(x => x.Thing))
   .Subscribe();
```

## When to suppress warnings

Suppress only where the two calls genuinely need different configuration for the same property (for
example, different throttling on each) and can't be consolidated into a single call — a narrow case,
since a single `AutoRefresh` call already accepts a buffer and a throttle.

## Suppress a warning

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage("Performance", "RSA3005:AutoRefresh already applied for this property", Justification = "<explain why>")]
```

```csharp
#pragma warning disable RSA3005 // AutoRefresh already applied for this property
#pragma warning restore RSA3005
```

```ini
[*.cs]
dotnet_diagnostic.RSA3005.severity = none
```
